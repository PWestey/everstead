## Collection receipts

Collection readiness captures a fixed, immutable reward payload: manifest, release, definition, source, classification, target, facility, and basis points. Old/new totals are not part of that permanent payload. A refreshable preview derives old/gain/new immediately before commit and binds the current receipt-chain anchor. This permits two banked non-expiring rewards for the same pool to be claimed in either order: the second uses the same reward payload with a refreshed preview.

Finalization requires an active immutable grant included in an authenticated release manifest. Payloads and receipts bind an immutable per-release package hash, while the durable root separately binds the current aggregate authority. Appending a new release therefore does not rewrite old receipts or invalidate a banked payload from an unchanged earlier release. Finalization refuses stale previews, release-package changes, duplicate definitions or source IDs, shared permanent-alternative targets, or a limited reward whose equivalent permanent alternative has already been claimed. Refusal returns the original state and zero reward applications.

Detailed receipts are bounded to 16. Folding occurs in batches of eight and preserves:

- exact per-pool and per-facility totals;
- contribution count;
- release and classification provenance;
- the folded tail identity needed by the next receipt;
- permanent claimed-definition replay authority.

There is no Collection lifetime cap or overflow conversion. Release budgets are authoring targets, not runtime or lifetime caps, and future releases continue to contribute. Mandatory requirements are balanced against permanent-only ownership and never depend on limited-event bonuses. All percentage grants use integer basis points. Additive formula helpers add the adjacent authored and Collection pools before applying them once to the unboosted base; they never multiply an already-boosted total. Integer and exact binary-fraction bases use BigInt-backed rational arithmetic. The returned numerator/denominator pair is the exact authority. `rounding: none` emits a numeric value only when the rational is exactly representable as a binary JavaScript number; otherwise it refuses and requires an explicit settlement rounding mode. All rounding modes reject unsafe results. Long-horizon gates cover cumulative totals through +1,000%.

Any future active release must be content-backed and evidence-complete. Its immutable, increasing release sequence is part of its release-package hash; each receipt, pending payload, preview, and folded release provenance retains that per-release package hash as later releases are appended. The validator requires non-reserved dependencies, locked Rank IDs and triangular EXP totals, explicit `active-content-backed` Rank rows, a zero/median/high-permanent/high-all fixture set with identical requirement-table IDs and derived contributor totals, `limitedContentRequired: false` for mandatory progression, and identities binding the predecessor scaling authority, approved simulation package, content, Rank rows, Collection grants, fixed requirement tables, and permanent-only fixture profile. The high-all fixture selects exactly one reward route for every permanent/limited alternative pair; permanent-only fixtures include neither limited nor future/inactive contributors. A self-consistent but repriced or still-reserved Rank row fails closed.

The simulation-package registry retains Phase 24B as a provisional baseline only; its false runtime-curve flag is not an approval to load or change a runtime curve. An active release pins a separately approved private-candidate package. Approval is scope-derived: Rank rows or new requirement tables require requirement approval; Collection grants require Collection-grant and throughput approvals; an unrelated runtime-curve flag is neither inherited nor consumed by this inactive package. New requirement tables are additive, reference only release-scoped content dependencies, and cannot reprice any inherited frozen table.
